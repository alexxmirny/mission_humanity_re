05 The code — a coverage heatmap

Every cell is an equal slice of the executable's machine code (~1.25 KB of instructions) — data / padding gaps are skipped, so the grid's size is proportional to how much code exists. Cells run in address order, 0x410000 top-left to 0x66f000 bottom-right. Colour is how researched that slice is; slate cells are code that's still unknown. Switch the colouring to ours to see the same grid by how much of each slice has been reimplemented in C++ (section 06) — same cells, same order, so the two are a direct visual diff of understood against rewritten. A cell that bridges a layout gap covers a wider address range (flagged on hover). 06 Reimplementation — how much of the game is ours

Every section above answers “how much of this binary do we understand”. This one answers a different question: how much of it has been rewritten in C++ and lives in src/mh_dll. Ours means a reimplementation exists and was proven equivalent — a migration-ledger row at verified, or a pre-ledger subsystem whose body is installed over the original. Planned means a ledger has claimed the function and scheduled it into a batch, but it is not proven yet. Functions settled as dead — deliberately never to be migrated — are in neither bucket.

07 Reimplementation by subsystem

The same bars as section 01, measured on the same attributed bytes, but filled by ownership instead of coverage: solid is ours, pale is planned, the rest is still the original binary’s. Rows with nothing in either bucket are folded away — for most of them that is the intended end state, not a gap: the target architecture keeps render, UI and platform in the original executable and migrates the deterministic spine.
