# (9806a28e / 05acccbc / e758413a) were seated fine and then desynced at the first sample or froze at
# committed 6060, because every 2nd match in one process entered session_begin_multi with the previous
# match's residue (stale gclk, P[1..] relations zeroed on the host, p54bc=0 on the joiner). The walk up to
# the re-joined lobby is a verbatim copy of mp_host_rematch.txt (its comments explain every step); the
# captures are renamed so this pair has baselines of its own. Pair with mp_client_rematch2.txt.
#
# THE ASSERTION IS THE post_check (tools/check_rematch_residue.py), not the pixels: game 2's
# PLAYERDUMP[sbm] must show gclk=0, p54bc=2 and the same rel bytes as game 1's on BOTH peers, and game 2's
# [desync] rollup must read 0 mismatching / >=1 compared. `gameclock 12000` on both peers is the freeze

# U19c (2026-09-18): UNPINNED, this walk runs in the SHIPPING configuration -- `[net]
# graceful_leave=1` is the default since U19, so by the time the CLIENT's own ESC->Quit->Yes reaches
# `signal cliquit` (which fires only after ITS main menu has settled, well after the wire frame was
# already sent), the departure has already reached US over the wire and ended OUR match too. This

# dialog. RE'D via ReVA on /eng/mh.exe: the dialog's main button (label "Ok", per U19's own dump)
# runs llm_ui_outcome_report_close_to_hud (0x004c6506), which fades back to the GAMEPLAY HUD, not
# the main menu -- so dismissing it is a NECESSARY first step, not a substitute, for the ESC->Quit
# ->Yes walk this scenario always needed to reach the menu and re-create.
#
# THE PREDICATE IS BORROWED FROM mp_host_gquit.txt (U19), which dumped this same dialog's widget
# list on 2026-09-18: "Continue game" gates its presence exactly as it does there.
present Continue game

# MEASURED 2026-09-18 (conductor, four probe runs with `dump`): the first Ok does NOT return to
# the HUD. It opens the OUTCOME REPORT -- the buildings/units stats table over the ending backdrop,
# list 0x00653D77, titled with the end-of-match reason ("You are the last player !" here: U19d's
# corrected wording, read off the frame) -- and that screen has its OWN Ok (widget [4], centre
# (320,337)). Clicking it starts the menu slide (origin 47 -> 9 one frame later, input_lock still
# 150) and the slide lands on the MAIN MENU (list 0x00653A7F: values 105/103/110/116/108/99/113),
# NOT the HUD: the match is over, so retail never returns to gameplay. That is why the old
# in-match ESC -> Quit game (113) -> Yes (121) walk cannot be used here -- on the main menu value
# 113 is EXIT, and `gamemode 2` never holds again. Wait for the table's Ok to settle (the first
# dialog is gone, so the only settled "Ok" is the table's), click it, then gate on the main menu.

# The table's Ok starts the slide but the OUTCOME REPORT stays the active list (dlg flag 0x33 held,
# the main-menu widgets already exist behind it and `settled value:110` matches them -- yet a click

# The main menu is still SLIDING IN when value:110 first settles (measured: `clickv 110` sent 0.6 s
