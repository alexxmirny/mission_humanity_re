# mp:SES3 -- the camera-latch trace, reproduced on the rig: pin the cursor against a screen edge,
# watch `_G_LLM_CAM_EDGE_LEFT_ACTIVE` latch and the camera scroll while the cursor does not move,
# then release it and watch the latch fall.
#
# WHY THIS SCENARIO EXISTS. The stuck-strategic-scroll report (mp:SC2) does not reproduce here, so
# the fix has to come out of a player's log -- which is only possible if the line the player sends
# already carries the latch state. This run is what proves the instrument works: it manufactures the
# H1 shape (a cursor that stops moving while it is still AT the edge) and requires the trace to show
# it, and it also requires a normal scroll's flags to RISE AND FALL so a build whose latches were
# simply never cleared could not pass.
#
# THE ASSERTION IS THE post_check, NOT THE PIXELS -- same shape as module_absent. `s0_menu` is a
# boot-sanity frame taken before the walk (the main menu, the most stable frame in the game); every
# claim this scenario makes lives in `tools/check_cam_trace.py` reading the `; [mtrace]` lines. An
# in-game capture would have been the wrong arm twice over: the camera has deliberately MOVED by
# then, and the HUD's unit sprites carry a wall-clock animation phase (see tutorial_enter's note on
# what that costs).
#
# WHY `cursorhold` AND NOT `cursor`. llm_input_mouse_delta_pump (0x00426645) RESETS
# _G_LLM_CURSOR_X/Y to _G_LLM_CURSOR_MENU_X/Y at entry and only an event in the ring overwrites
# them, so a single `cursor` event moves the cursor for exactly one frame. Holding = re-injecting
# every present, which is also what a clamped VM pointer really does (the VM-input page section 9c measured
# 558 events arriving while the accumulator sat pinned at the clamp).
#
# THE LEFT EDGE, deliberately. The left/up tests are `_G_LLM_CURSOR_X == 0` exactly, while the
# right/down thresholds are `(WindowWidth-1) - margin` with a margin that depends on the HUD width
# and on whether an LMB drag is in flight -- an unambiguous predicate makes a failure mean the
# latch, not the geometry. And the strategic camera WRAPS (`& general.width_mask`), so scrolling
# left at column 0 keeps moving rather than stopping at a map edge.
#
# Single-peer, same menu walk as groupmove_minimap.txt / res_hud.txt: seat an AI in slot 1 and Start
# alone, so the real menu -> lobby -> launch path runs with no client VM.

settled value:110
capture s0_menu
clickv 110
present Player name
settled Ok
clickl Ok
settled Create
clickl Create
present Game name
settled Ok
clickl Ok
present Available maps
settled Ok
clickl Ok

# host lobby: OPEN -> AI on slot 1, gated on the "Computer" name label because the per-slot spinner
# rebuilds the widget list (a click fired mid-rebuild misses).
present Network players
settled Start
click 70 132
present Computer
enabled Start
clickl Start

# In-game. `gameclock` rather than a frame count: the edge scroll is paced by CURRENT_GAME_TIME
# against _G_LLM_CAM_EDGE_LEFT_INTERVAL, so the thing the hold has to outlast is game time.
absent Network players
gamemode 2
gameclock 2000

# 1. CENTRE -- the control. All eight latches clear, camera still.
cursorhold 320 240 60

# 2. PINNED AT THE LEFT EDGE. EDGE_LEFT_ACTIVE latches on the first frame and stays latched while
#    the cursor does not move; the camera scrolls the whole time. This is the shape check_cam_trace
#    calls "edge-latched while pinned", and --expect-pinned is what requires it.
cursorhold 0 240 600

# 3. RELEASED. The else-branch in llm_strat_input_update clears the flag on the first frame the
#    cursor is off the edge -- the FALL half of --expect-rise-fall.
cursorhold 320 240 120

log cam_edge_scroll: pinned at x=0 for 600 presents, then released -- read the edge=/held=/cam= columns
end
