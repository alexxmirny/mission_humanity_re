# mp:D36 HOST -- the rc4 field match's shape: this process plays a match on map A in which it LANDS
# its mother ship, the match ends, and the SAME process hosts a second match on a map with a SHORTER
# name against a FRESH client process. Pair with mp_client_d36_match1.txt (client1, plays match 1 and
# quits to desktop) and mp_client_d36_fresh.txt (client2, a brand-new process launched into client1's
# lane after that exit -- test_ui.py's client_after_exit / client_shares_lane).
#
# WHY THIS SHAPE AND NOT rematch_play's. rematch_play (mp:RM1) rematches the SAME joiner process and
# neither peer lands, so both carry identical (zero) residue and it could never see D36. The rc4 host
# (01a0deb9) had landed in its 28 s Magnetic Fields match; the landing grant books +5400/4000/3000/2000
# into player_data.resource_spent (gains-only, never cleared for a human -- mp:D36), so its second
# match entered with that grant while the fresh joiner entered with zeros: `DESYNC step=50
# first_region=8 p0_ai_econ`. The shorter second map name is the second residue: Planets[31]'s string
# slots keep the old name's tail past the new NUL (`planets` +0x81da in rc4).
#
# THE ASSERTION IS THE post_check (tools/check_d36_rematch_seed.py): the host's match-2 step-1 seed
# (mh_match_seed.bin) equals the fresh client's over player_data + planets + players +
# player_resources, the in-band [desync] watch says nothing, both first samples agree -- and the
# mh.dll clear logged `nonzero=0` on every first-in-process entry and >0 on the host's rematch entry
# (so a run where match 1 never landed cannot pass vacuously).
