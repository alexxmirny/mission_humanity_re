# WHY: D17's acceptance clause wants mp_order_diff evidence that both peers release the
# CTL_RESYNC_BEGIN synthetic order (kind 0xf0) on the SAME step. That order only exists when
# llm_net_lockstep_force_resync runs, and on the rig it never does.
#
# WHAT WAS MEASURED (2026-08-27), each a 2-peer --determinism run with --record:
#   * healthy LAN, default knobs            -> kind 0xf0 NEVER SCHEDULED
#   * 200 ms RTT via --shim-delay 100       -> kind 0xf0 NEVER SCHEDULED

#     stalls, each under the ~10 s             (the stalls themselves part the order streams --
#     rx_timeout_ms so the link survives)       a different effect, not this one)
#
# WHY IT CANNOT FIRE HERE, from the counter rather than from argument. `[net] fix_audit=400` prints
# `trig=<RESYNC_TRIGGER_COUNT> countdn=<SYNC_RETRY_COUNTDOWN>`, and across every run above it read
# `trig=0 countdn=59-60`. countdn sits at its 0x3c reload, so the at-horizon WAIT path never runs;
# RESYNC_TRIGGER_COUNT only increments on the type-3 ACKs that path emits, so it stays 0, and
# force_resync's threshold (ACTIVE_PLAYERS*100 < trig) is never approached. Inducing latency does not
